\section{Introduction}
\label{sec:intro}

Large language model (LLM) agents are increasingly deployed as autonomous
software engineers~\cite{jimenez2024swebench,yang2024sweagent}, long-context
assistants~\cite{wu2024longmemeval}, and conversational
companions~\cite{maharana2024locomo}. Their effectiveness is largely
determined by \emph{harness engineering}---the design of the surrounding
code that orchestrates memory, retrieval, prompt routing, and tool
use~\cite{lee2026metaharness}. Automating this design through
propose--evaluate loops, where a second LLM (the \emph{proposer})
iteratively improves the harness, has emerged as a promising
paradigm~\cite{hu2024adas,khattab2023dspy}.

Existing approaches span a spectrum of information exposure. At one end,
systems like ACE~\cite{zhang2025ace} and
OpenEvolve~\cite{sharma2025openevolve} compress iteration history into
summaries or curated playbooks, feeding the proposer a lossy but compact
view. At the other end, Meta-Harness~\cite{lee2026metaharness} takes the
opposite stance: it deploys a coding agent (Claude Code) as the proposer
with full filesystem access to all prior candidates, scores, and traces,
arguing that a capable agent's native browsing and reasoning already
constitute an effective search gradient---more information enables better
optimization.

We share this latter intuition: a coding agent's chain-of-thought
\emph{is} the optimization gradient, and its ability to autonomously
navigate large workspaces makes it a natural proposer. Building on this
foundation, we observe that the proposer's effectiveness can be further
improved by actively managing which files it attends to. As harnesses
grow in complexity---often spanning dozens of source files, configuration
schemas, and diagnostic logs---we identify three opportunities where
curated context outperforms unrestricted access:
\begin{enumerate}
    \item \textbf{Attention focus.} Restricting the visible workspace to
    high-relevance files concentrates the proposer's attention on the
    current optimization frontier, reducing distraction from low-utility
    files.
    \item \textbf{Directed exploration.} Explicit mechanism-level
    guidance steers the proposer toward structurally distinct alternatives
    (e.g., retrieval re-ranking, memory consolidation) rather than
    repeatedly revisiting familiar axes such as prompt wording.
    \item \textbf{Optimization direction.} A narrower, curated view
    sharpens the proposer's search gradient---analogous to how
    CODEFILTER~\cite{li2025codefilter} shows that filtering retrieved
    context to only positive-impact chunks improves code completion over
    providing all retrieved files.
\end{enumerate}

Our key insight is that \emph{optimizer attention should be managed the same
way a skilled developer manages their own}: start with a focused view that
covers only the most relevant files and the strongest reference points, then
broaden context only when the narrow view stalls. We introduce
\textbf{Optimization Harness}, a modular framework that wraps any
propose--evaluate loop with three capabilities: (i)~Docker file-scope
sandboxing that restricts the proposer to a curated workspace,
(ii)~mechanism-level optimization-focus prompts that steer exploration along
named axes, and (iii)~labeled best/worst reference iterations that provide
imitation targets and anti-patterns. Building on this framework, we propose
two adaptive context-selection policies: a \emph{progressive} policy that
runs a budget state machine
(\texttt{low}$\,\to\,$\texttt{medium}$\,\to\,$\texttt{high}), escalating
only after a Pareto-frontier stall and resetting on every improvement; and
a \emph{bandit} policy that models each workspace file as a multi-armed
bandit arm with a per-file UCB scorer and Beta-smoothed prior,
concentrating high-utility files in a curated ``hot workspace'' each
iteration.

We evaluate Optimization Harness across three benchmarks spanning
conversational memory (LoCoMo), long-context retrieval (LongMemEval), and
software engineering (SWE-bench Verified), using two proposer families
(Claude Code with Kimi K2.6, and Codex GPT-5.4). Our progressive policy
outperforms the fixed-high default in five of six (benchmark, proposer)
cells. The bandit policy achieves the single strongest result: lifting
SWE-bench Verified from 0.44 to 0.64 (+20\,pp) on the full 500-task split.
Across ten adaptive training runs, 35 of 48 score-improvement events occur
at \texttt{low} or \texttt{medium} budget, and after warm-up the
per-opportunity breakthrough rate at \texttt{high} (9\%) does not exceed
that of \texttt{low} (11\%) or \texttt{medium} (11\%).

These results demonstrate that \emph{managing what the optimizer sees} is
a complementary and effective lever to improving the optimizer
itself---yielding up to +20\,pp gains without changing the underlying
proposer model. Our contributions are:
\begin{enumerate}
    \item We formalize the problem of \emph{proposer context management}
    in harness optimization and identify three axes along which curated
    context improves over unrestricted access.
    \item We introduce Optimization Harness, a modular framework with
    Docker sandboxing, mechanism-focus prompts, and reference labeling
    that enables pluggable context-selection policies.
    \item We propose two adaptive policies (progressive and bandit) that
    implement graduated context disclosure, and evaluate them on three
    benchmarks with two proposer families, demonstrating consistent
    improvements over the fixed-high baseline.
    \item We provide an empirical analysis of where optimization
    breakthroughs occur across budget tiers, showing that curating
    attention is more efficient per opportunity than maximizing context.
\end{enumerate}
