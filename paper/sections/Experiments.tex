\section{Experiments}
\label{sec:experiments}

We evaluate \name by separating the two context-curation strategies it
introduces. The iteration-level strategy bounds and labels the history seen
by the proposer; the file-level strategy then reallocates attention inside
the exposed workspace. The two are not independent additive modules; both
route the same bounded proposer attention, only at different granularities.

\subsection{Setup}
\label{sec:setup}
\textbf{Benchmarks.}
We use two long-horizon memory benchmarks and one software-engineering
benchmark. LoCoMo~\cite{maharana2024locomo} probes multi-session conversation
memory; we optimize on 80 training examples and report on the full
1,449-example split. LongMemEval~\cite{wu2024longmemeval} probes retrieval,
temporal reasoning, and consolidation over long histories; we optimize on
100 training examples and report on the 400-example test split. SWE-bench
Verified~\cite{openai2024swebenchverified} probes multi-file coding-agent
harnesses; we optimize on \texttt{trainfirst30} and re-evaluate selected
candidates on the full 500-issue verified set.

\textbf{Harnesses and proposers.}
On the memory benchmarks the inner harness is a MemGPT-style memory
agent~\cite{packer2023memgpt}. On SWE-bench the inner solver is a fixed
Mini-SWE agent driven by DeepSeek~v4 Flash, which isolates harness-curation
effects from solver changes. We instantiate the outer proposer with two
coding-agent scaffolds: a Codex CLI proposer with GPT-5.4 (\emph{codex54})
and a Claude Code-compatible proposer with Kimi~K2.6 (\emph{claudekimi}).
Both run on the memory benchmarks; SWE-bench uses claudekimi only.

\textbf{Baselines and reporting.}
The end-to-end baseline is \textbf{Full-context}, the default Meta-Harness
configuration~\cite{lee2026metaharness}: every iteration exposes the full
revision history and an unrestricted file tree, with no best/worst labelling.
On LoCoMo and LongMemEval, each (benchmark, proposer, policy) cell is run
three times for 30 propose--evaluate iterations. We report test mean$\pm$std
across runs, the best held-out passrate, and per-propose token cost on the
best-by-test run. SWE-bench is reported separately, since it is a single
20-iteration run with a different cost profile.

\textbf{Iteration-level curation improves search quality.}
Progressive lifts mean held-out passrate over full-context in all four
memory cells: $+2.3$\,pp on LoCoMo claudekimi, $+4.3$\,pp on LoCoMo codex54,
$+0.7$\,pp on LongMemEval claudekimi, and $+0.25$\,pp on LongMemEval codex54.
The LoCoMo gains are clear relative to run variance; the LongMemEval gains
are smaller and should be read as directional. The iteration-axis signal
alone therefore improves search without any file-level utility model.

\textbf{File-level curation improves the operating point.}
\name is cheaper than full-context in all four memory cells and the cheapest
policy in three of them, strictly improving both cost and best-test quality
over full-context in those three. The exception, LongMemEval/codex54, is an
informative trade-off: \name reaches a $-26\%$ cost point at a $-3.5$\,pp
best-test quality drop. The file axis should therefore be read as
Pareto-frontier expansion rather than a universal dominance guarantee.

\subsection{SWE-bench with Mini-SWE}
\label{sec:swe}

We report SWE-bench separately because this experiment departs from the
memory protocol in three ways: it was run once, it used 20 optimization
iterations rather than 30, and its best curated runs spent more tokens per
proposal than full-context. Despite the higher cost, the verified-set gain
is the largest effect we observe.

The SWE-bench result clarifies what curation is and is not optimizing.
Curation is not simply a token-reduction mechanism: Progressive and \name
spend more tokens than full-context here. The curated context instead
induces a different search trajectory. The proposer appears to use the
narrower, labelled history to inspect more source and candidate evidence
relevant to repair; this costs more tokens but yields a better harness on
the full verified set.

\subsection{Mechanism: labels redirect a fixed inspection budget}
\label{sec:mechanism}

The introduction already noted that workspace size grows much faster than
the proposer's actual read count. Here we focus on where those reads land.
For every Read call into \texttt{reference\_iterations/iter\_M/}, we
classify whether iter~$M$ was the current top-$1$ or top-$3$ candidate by
passrate at prompt-build time, and whether it sat among the three most
recent prior iterations.

Progressive pulls reference reads toward the current best iteration: top-$1$
share rises by $+25.6$\,pp on LongMemEval and $+22.7$\,pp on LoCoMo. LoCoMo
additionally shows a $-23.1$\,pp drop in recent-$3$ share, so labels do not
merely add attention to strong candidates; they can also pull attention away
from the default recency prior.

This also explains why always staying at \texttt{low} is not enough. At
\texttt{low} and \texttt{medium}, Progressive supplies compact best/worst
labels useful for exploiting a known direction. As the run proceeds, the
proposer must reason about more prior edits, regressions, and interactions
among files. When progress stalls, opening \texttt{medium} or \texttt{high}
gives the proposer enough historical evidence to grasp what has already
changed and avoid locally plausible but redundant edits. The dynamic
schedule treats low budget as a focus mechanism, not as a permanent
information cap.

\subsection{Ablation: how do the strategies interact?}
\label{sec:ablation}

We run two ablations to separate bounded historical exposure, labelled
historical attention, and file-level utility guidance. First, on
LoCoMo/codex54 we compare full-context against three bounded
iteration-selection rules: Random@$3$, Recency@$3$, and Progressive.
Second, on claudekimi memory runs we force the bandit budget to stay at
either \texttt{low} or \texttt{high}.

All bounded variants beat full-context on LoCoMo/codex54, so part of the
gain comes from avoiding unstructured full-history browsing. The
force-budget rows show why the dynamic policy still matters: force-low
nearly closes the reference-history channel, while force-high pays more
tokens to keep it open. LongMemEval carries enough file-level signal for
force-low to do well on train, whereas LoCoMo benefits from explicit
historical examples. The policy must therefore expand when later
iterations need broader evidence, yet should not spend the whole run at
high budget when a compact context suffices.
