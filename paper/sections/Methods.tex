\section{Method}
\label{sec:method}
This section describes \name, our framework for online context curation in
automated harness optimization. \name builds on the observation that prior outer-loop systems either expose
the full optimization history as a monolithic
filesystem~\cite{lee2026metaharness} or compress it into lossy
summaries~\cite{yang2024opro,lee2025feedback,agrawal2025gepa}. Neither static
rule is well calibrated to the search trajectory: which prior artifacts
matter depends on the proposer's current iteration, its recent edits, and
the regressions it has just observed. \name
instead curates context through two composable strategies acting at different
granularities. The iteration-level strategy controls the historical scope by
selecting which prior rounds' artifacts to expose. The file-level strategy
then reallocates read effort within the exposed workspace, prioritizing files
whose inspection has previously correlated with productive edits. The
file-level strategy is therefore not a standalone replacement for
iteration-level curation: on its own it does not decide which prior
iterations, traces, or candidate histories should enter the evidence
workspace.

\subsection{Problem Statement}
\label{sec:setting}
\textbf{Objective.}
A harness is a stateful program that wraps a fixed language model $M$ and determines what context $M$ sees at each step. Following~\cite{lee2026metaharness}, for a harness $H$ and task instance $x \sim X$, we sample a rollout $\tau \sim p_M(H, x)$ and score it with task-specific reward $r(\tau, x)$. Automated harness optimization seeks
$$
H^* = \arg\max_H \mathbb{E}_{x \sim \mathcal{X}, \tau \sim p_M(H, x)} r(\tau, x).
$$

\textbf{Search loop with context curation.}
A run of the outer loop produces a sequence of evaluated candidates $\{(H_i, E_i)\}_{i=1}^t$, where $E_i$ bundles $H_i$'s source code, scores, and execution traces. We call the accumulated archive $D_t = \{(H_i, E_i)\}_{i \leq t}$ the experience pool.
At iteration $t$, the proposer $\mathcal{P}$ generates a new candidate conditioned on a curated context $C_t \subseteq D_t$:
\begin{equation}
H_{t+1} \sim P(\cdot \mid C_t),
\label{eq:search_loop}
\end{equation}
where $C_t = \mathcal{C}(D_t, s_t)$ comes from a context curation policy $\mathcal{C}$ that selects which subset of $D_t$ to surface, and $s_t$ denotes the proposer's auxiliary state at iteration $t$ (e.g., current frontier, recent regressions).
After evaluation, $D_{t+1} = D_t \cup \{(H_{t+1}, E_{t+1})\}$. This formulation generalizes prior work: Lee et al.~\cite{lee2026metaharness} corresponds to direct filesystem access ($C_t = D_t$), while Agrawal et al.~\cite{agrawal2025gepa} and Yang et al.~\cite{yang2024opro} use static compression ($C_t = \phi(D_t)$ for fixed $\phi$).

\subsection{\name}
\name is a closed-loop controller for sequential context selection. At each iteration $t$, the controller (i) maintains a state $s_t$ summarizing past outcomes, (ii) computes scores $Q_t$ for candidate historical artifacts and files in $D_t$, and (iii) applies a selection rule $\pi$ that maps these scores to the curated context $C_t$ in Eq.~\ref{eq:search_loop}. After the evaluator returns $E_{t+1}$, the controller updates its state using a reward signal $\rho$ before the next proposal. The rest of this section defines the shared state, scoring, selection, and update interface; the following subsections instantiate it as the Progressive and bandit policies.

\textbf{State.} The controller's state has two components matching the two curation granularities, $s_t = (U_t, B_t)$. $U_t$ is an \emph{iteration-level summary} that tracks how recent proposals have fared against the Pareto frontier---for instance, whether the last iteration was an improvement, or how many iterations have passed without one. $B_t$ holds \emph{per-file usage statistics}: for each file in the workspace, how often it has been read in past iterations and the cumulative reward attributed to those reads.

\textbf{Score.} Given $(D_t, s_t)$, \name estimates the expected value of surfacing each artifact for the next proposal, weighed against the inspection cost it would impose.

\textbf{Selection.} The selection rule turns these scores into an evidence workspace for the proposer. Depending on the instantiated strategy, this workspace may include labelled reference iterations, trace summaries, file-level hints, or any combination of these signals under a budget tier.

\textbf{Update.}  Once the evaluator returns $E_{t+1}$, \name computes a scalar reward $\rho_{t+1}$ summarizing whether the new harness improved the search, updates the Pareto frontier, and refreshes $s_t \to s_{t+1}$. The refreshed state shapes the next round's scoring and selection.

We instantiate this framework as two concrete policies at different granularities: an
\emph{iteration-level} policy deciding \emph{which prior rounds} to surface, and a \emph{file-level} policy deciding \emph{which files inside the exposed workspace} receive priority.


\subsection{Iteration-level curation.}
\label{ssec:iteration}
Not every past iteration is equally informative, and its value shifts with the proposer's current trajectory. After a successful update that extends the Pareto frontier, the proposer benefits most from the recent winning candidates, which reinforce the direction that just worked. After a streak of failed attempts, the proposer needs a broader view: exposing earlier failures and their traces can surface overlooked failure modes and prompt qualitatively different edits.

We operationalize this intuition through a \emph{budget tier}
$b_t \in \{\texttt{low},\, \texttt{medium},\, \texttt{high}\}$ that controls how much of the experience pool $D_t$ is surfaced to the proposer.  Table~\ref{tab:budgets} specifies the context exposed at each tier: at \texttt{low}, the proposer sees only the single best-scoring candidate, the single worst-scoring one, and the most recent evaluation trace; at \texttt{high}, it receives the full history.

\centering

\caption{Budget tiers and the context they expose to the proposer. ``Reference iters'' determines which prior candidates are included; ``Trace scope'' controls how many recent per-task evaluation traces accompany each reference bundle.}
\begin{tabular}{@{}lccc@{}}
\toprule
 & \texttt{low} & \texttt{medium} & \texttt{high} \\
\midrule

\end{tabular}
\label{tab:budgets}

The tier follows a \emph{progressive} schedule keyed to the reward signal $\rho$ (Section~\ref{sec:method}). The budget starts at \texttt{low}. Whenever a proposal fails to improve on the current Pareto frontier ($\rho_{t+1} \leq 0$), the tier is promoted by one level, gradually widening the proposer's view of the experience pool. When an improvement is observed ($\rho_{t+1} > 0$), the tier resets to \texttt{low}, since a lean context suffices to refine the direction that just worked. This schedule realizes a simple explore--exploit tradeoff: the controller stays at a narrow context by default and only widens exposure when progress stalls.

\subsection{File-level Curation.}
\label{sec:bandit}
The file-level strategy treats readable files as arms in a delayed-credit
bandit. Its scope is deliberately narrower than the iteration policy: once an
evidence workspace has been assembled, it ranks files inside that workspace
so the proposer sees a short hot list rather than an undifferentiated tree.
The policy records which files were read before each proposal, assigns those
reads a reward after evaluation, and uses the resulting utility estimates to
build the next hot workspace. Figure~\ref{fig:file_bandit_pseudo} gives the
procedure in pseudocode.

\centering

\small
\textbf{File-level curation.}
\begin{enumerate}[leftmargin=1.2em,itemsep=1pt,topsep=3pt]
\item Given archive $D_t$, frontier $F_t$, file stats $B_t$, and stagnation
count $g_t$, choose budget $b_t$: \texttt{low} if no file stats,
\texttt{high} if $g_t \ge 4$, otherwise \texttt{medium}.
\item Select reference iterations from $D_t$ according to $b_t$.
\item For each readable non-core file, estimate utility from smoothed success
rate and mean delayed reward; penalize large reads and add a UCB bonus.
\item Pin core harness files, mark top-scored files as \texttt{hot}, and mark
the next group as \texttt{warm}.
\item Run the proposer with selected references, pinned files, and hot/warm
hints.
\item Evaluate the candidate; attribute reward to files read by the proposer;
update $B_{t+1}$ and $g_{t+1}$.
\end{enumerate}
\end{minipage}}

The schedule is dynamic because the useful scope changes during search.
Keeping every iteration at \texttt{low} is cheap but closes the
reference-iteration channel exactly when later proposals need to understand
earlier design changes and avoid repeating exhausted edits. \texttt{Medium}
keeps a compact set of high-value references open; \texttt{high} is reserved
for stagnation, when the proposer benefits from a wider view of previous
candidates and traces. Once an improvement is found, the controller returns
to narrower context, since the next edit is again anchored by a recent
productive direction.
