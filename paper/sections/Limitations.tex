\section{Limitations}
\label{sec:limits}

Our results support context curation as a design principle rather than
universal dominance for any single policy. The number of retained runs per
cell is small, so we avoid significance claims on individual cells and
instead report run means, standard deviations, and best-by-test operating
points. The file-level strategy also shows benchmark- and proposer-dependent
trade-offs: it often opens lower-cost operating points but can sacrifice
passrate when the uncurated file pool already carries strong signal or when
guidance metadata is layered on top of a large exposed history.

The proposer itself is a black-box coding-agent optimizer. Both Claude
Code-compatible and Codex CLI-compatible proposers carry model behaviour,
system prompts, tool-use policies, and implementation details that \name
cannot fully control. Our policies bias the proposer's behaviour
distribution by changing which iterations and files are salient, but they
cannot force a particular sequence of tool calls or guarantee that the
proposer uses the provided hints. This matters for cost interpretation. On
SWE-bench, curated runs consume more tokens than full-context while also
reaching substantially higher verified-set passrate. The policy appears to
redirect the proposer toward more useful inspection, yet a more controllable
proposer interface could expose a cleaner trade-off between passrate and
token budget.

The ablations are necessarily narrower than the main evaluation. The
Random@$3$ and Recency@$3$ iteration-selection ablations are anchored on the
LoCoMo / codex54 setting, while the force-budget analyses focus on retained
claudekimi runs. The read-target mechanism analysis is most detailed for
claudekimi because its tool traces expose per-file read targets; codex54
logs bucket more activity under a single shell interface, which limits
comparable file-level attribution. Finally, \name is evaluated on three
agent-harness families, but all experiments use a fixed outer-loop length and
a fixed set of proposer backbones. Larger run budgets, additional proposers,
and broader task families may shift the cost--quality frontier and should be
tested before treating the observed trade-offs as deployment defaults.
