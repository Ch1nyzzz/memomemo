\section{Introduction}
\label{sec:intro}

Agent \emph{harnesses}---the code that wraps a large language model
(LLM) into a working agent---largely determine agent performance. Two
agents built on the same LLM but with different harnesses can differ by
up to $6\times$ on the same benchmark~\cite{tian2026swe}. This gap has
motivated \emph{automated harness optimization}: an outer loop in which
an LLM-driven proposer iteratively suggests candidate agents, prompts,
or memory components, and an evaluator scores each candidate to guide
the next proposal~\cite{romeraparedes2024funsearch,novikov2025alphaevolve,sharma2025openevolve,agrawal2025gepa,lee2026metaharness}.

Most prior approaches inherit the information bottleneck of text
optimization~\cite{hu2024adas,sharma2025openevolve,zhang2025ace}.
Feedback from earlier runs collapses into scalar scores, short summaries,
or the most recent candidate~\cite{novikov2025alphaevolve,agrawal2025gepa,lee2025feedback,madaan2023self,yang2023large},
removing the details needed to trace downstream failures back to earlier
harness decisions~\cite{lee2026metaharness}. Meta-Harness lifts this
bottleneck by replacing the proposer with a coding agent equipped with
developer tools and exposing the full revision history as a navigable
filesystem~\cite{lee2026metaharness}. The meta-agent can inspect raw
code, execution traces, and diffs before proposing the next edit.

Full access, however, is not effective access. As the optimization
horizon grows, the filesystem accumulates prior candidates, failed
edits, traces, and summaries, and the proposer must repeatedly judge
which subset of that history bears on the current failure. Empirically,
scaling the exposed workspace does not scale the number of files read:
the proposer continues to open roughly the same small number per
iteration and only shifts \emph{which} files it picks. The bottleneck
is therefore attention placement rather than raw access. We reframe
automated harness optimization as an \emph{online context curation}
problem: before each proposal, the optimizer must decide which prior
iterations, trace details, and workspace files to make salient under
the proposer's limited inspection budget.

We introduce \textbf{\name}, a framework that treats this context
choice as a control variable in automated harness optimization. \name
sits between the optimization loop and the meta-agent and decides which
historical and file-level evidence should guide each proposal. The
framework supports two composable curation strategies. The
iteration-level strategy fixes the historical scope: it starts from a
small labelled set of high- and low-performing prior attempts and
widens exposure when optimization stalls. This strategy alone
suffices to improve mean held-out performance across our memory
comparisons. The file-level strategy then reallocates the proposer's
fixed read budget within the exposed workspace, using delayed reward
to prioritize files whose inspection correlates with productive edits.

This design does not require both strategies to be active. Both
address the same inspection bottleneck, only at different granularities.
Iteration-level curation changes which parts of the search history are
available and how they are labelled; file-level curation changes where
the proposer spends its bounded inspection effort inside the exposed
workspace. The two axes therefore need not produce independent,
monotonic, or uniformly positive effects. They are alternative and
composable ways to move the optimization loop along a cost--quality
frontier.

We evaluate \name on three benchmarks spanning agentic software
engineering and long-horizon memory: SWE-bench~\cite{jimenez2024swebench},
LongMemEval~\cite{wu2024longmemeval}, and LoCoMo~\cite{maharana2024locomo}.
Adaptive context curation improves held-out performance in most
(benchmark, proposer) settings. On the two memory benchmarks it opens
lower-cost operating points on the cost--quality frontier. On
SWE-bench Verified it instead trades a modest increase in tokens per
proposal for a markedly stronger final harness: the strongest curated
run reaches 0.640 passrate on the full verified set, against 0.440 for
the source harness and 0.458 for the full-context optimized baseline.
Mechanistic analyses show that the proposer reads roughly the same
number of files per iteration; only the target distribution shifts.
At the iteration level, \name pulls reference-history reads away from
a recency-biased default toward policy-labelled best/worst iterations.
At the file level, it shifts the cost--quality operating point of that
fixed read budget. Managing what the proposer attends to is therefore
a first-class design variable in automated harness optimization.
